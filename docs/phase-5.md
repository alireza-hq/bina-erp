# Phase 5: weekly locks and audit trail

## Period architecture and migration

Migration `0007_reporting_periods_and_audit.sql` adds reporting_periods and audit_logs with no destructive work/user/session changes. Periods have UUID id, unique week_start, week_end, OPEN/LOCKED enum, nullable lock owner/time, and creation/update timestamps. Database checks require Saturday plus exactly six days for Friday and consistent lock metadata. Valid week starts are in 2000–2099, matching the existing calendar domain. Unique Saturday starts and fixed week lengths eliminate duplicate/overlapping valid periods without a second calendar definition.

The existing `weekStart()` and `shiftDate()` functions define weeks everywhere. Missing rows mean OPEN, with derived dates and empty lock metadata. Reads and work saves do not materialize rows. Locking materializes a row; unlocking keeps it, clears current lock metadata and leaves earlier transitions in audit history. Unlocking an absent/open week is a no-op. No scheduled locking or weekly setup is required. Authorized explicit actions can target current/future weeks too; they otherwise stay open.

The migration was validated by isolated full-chain replay, including legacy archives and authentication preservation. Apply `pnpm db:migrate` to the reviewed target before deploying this code or using `pnpm admin:promote`; missing audit/period tables fail closed. No application database was migrated during this phase. Existing history starts without audit events; old state changes are not fabricated or backfilled.

## Authorization, concurrency and atomic editing

BUSINESS_ADMIN and IT_ADMIN can read/change period status via independently guarded GET `/api/admin/reporting-periods/[week]` and POST `/lock` or `/unlock`. EMPLOYEE cannot. The week string must be a real Gregorian Saturday; clients cannot supply an end date or arbitrary status. Mutation origin checks remain in force. The service rechecks the active actor's reporting role inside the transaction. Only actual transitions generate PERIOD_LOCKED/PERIOD_UNLOCKED; retries are idempotent.

All work-entry day reconciliation enters `assertReportingPeriodEditable()` inside its transaction, before employee and master locks. It acquires a shared transaction advisory lock with namespace 8172402 and the integer Gregorian week-start day. Period mutations acquire the same key exclusively before reading/upserting state. This coordinates even when there is no period row. Shared locks allow different employees to save in the same open week; an exclusive lock waits for in-flight saves. After a period lock commits, later saves read LOCKED and return 423 before changing any row. No role can bypass this check in the personal work-entry service.

Existing ownership, relationship validation, active-account checks and optimistic version checks remain. The employee/user administration row locks use FOR NO KEY UPDATE: they still serialize account edits/deactivation, while allowing audit foreign-key key-share checks. This avoids a needless FK lock inversion with concurrent master-data edits. Period actor checks use FOR SHARE. Locks and audit writes live through transaction completion, and PostgreSQL rollback handles failures.

## Audit events and transaction strategy

Audit rows contain id, nullable actor_user_id, action enum, entity type/UUID, old_data/new_data JSONB and timestamp. Four indexes support chronological pagination and actor/action/entity filtering. Actor FK uses RESTRICT to preserve attribution; entity ID has no FK because deleted work must retain its audit identity. Application code only inserts/reads audit rows. No update/delete/clear API exists. Database owners still have control; this is an operational trail, not a cryptographically tamper-proof ledger.

Work entries log individual CREATED/UPDATED/DELETED events after reconciliation but before commit. Selected payload fields include employee/date, project/file IDs, description and exact hour strings. Surviving IDs remain intact; no-op rows produce no event. Removed rows retain their before-data. One daily transaction commits all business rows and audit events or none.

Administrative events cover USER_ROLE_CHANGED, USER_DEPARTMENT_CHANGED, USER_ACTIVATED, USER_DEACTIVATED and USER_UPDATED for employee-code changes; DEPARTMENT/PROJECT/PROJECT_FILE CREATED, UPDATED, ACTIVATED and DEACTIVATED. A mutation affecting several categories can create multiple labelled events with the same selected before/after state. Unchanged patches produce no events. Previously nontransactional department/project writes are now transactional and lock their current row before capturing the before-state. Existing project-file/user transactions insert their events before commit.

The controlled promotion CLI records USER_ROLE_CHANGED with null actor and explicit `admin:promote operator command` source, because it has no authenticated application actor. Re-promoting an existing IT_ADMIN is a no-op. LDAP provisioning/synchronization and session creation are not newly audited; no LDAP password, directory DN, token, cookie, raw request body, email or login secret is stored by these audit paths. Field projection is centralized in `audit.ts`. Work descriptions and master descriptions are intentionally retained; audit size grows with changes and no retention purge is implemented.

## UI and reporting behavior

Employee weekly and daily pages show OPEN/LOCKED status. Locked editors disable project/file/description/hour editing and add/remove/save controls while preserving reading and date navigation. A newly locked stale form receives the Persian server explanation, retains drafts and becomes read-only. Refresh a previously open read-only page after an administrator unlocks the week.

`/admin/reports` displays a status/action panel only when the range is exactly Saturday–Friday. It shows lock owner/time and confirms the affected Jalali range before changing state. Custom partial or multi-week ranges offer guidance rather than a bulk lock action. Full audit access remains IT-only at `/system/audit` and GET `/api/admin/audit`; business admins see only current period metadata. The audit page filters actor-name/username, action, entity type and inclusive date range, with 25/50/100-row pages and expandable JSON before/after details. Default range is 30 days; filter dates are explicitly Gregorian and displayed event times use Jalali/Tehran. Stable created_at/id ordering and a read-only repeatable-read query keep page/count internally consistent.

Locked work remains readable, filterable, grouped and exportable without altering Phase 3/4 queries or XLSX structure. Lock/unlock changes no entries. **Current department attribution and current master names are not snapshotted.** Reassigning an employee can still change department-filter/group results for a locked week, and renamed references change labels. Total work hours and underlying work rows remain protected by the application lock; database operators/out-of-band SQL remain outside that protocol. Separate report/export requests can reflect later authorized unlock-and-edit activity. There is no approval, notification, dashboard, manager scope, payroll or Phase 6 feature.

## Validation and performance

PostgreSQL tests cover default-open behavior, week constraints/uniqueness, role restrictions, repeated transitions, stale create/update/delete and atomic day rejection, report/group/export totals of 10.5 while locked, restored editing after unlock, meaningful row before/after events, master/user events, and IT-only audit pagination/filters/JSON/FKs/indexes. Forced audit-insert trigger failures roll back work, period and master changes; forced enclosing business rollback also removes audit events. Production HTTP tests race a save with a lock, check subsequent mutations return 423, verify read-only pages and unchanged XLSX totals, test custom-range action hiding and reject non-IT audit access.

A local three-row reconciliation with update/delete/create audit events completed in about 39 ms in the isolated fixture. This is a small correctness/performance observation, not a concurrency load benchmark. Synchronous audit inserts are bounded by the existing 50-row/day limit; large audit history and actor substring searches may eventually justify retention/search tuning. Existing in-process login throttling and unpaginated IT master lists remain inherited debt. Native visual/browser and live LDAP credential checks remain manual; automated session/auth tests exercise the unchanged code.

Completed validation: `pnpm test` (14 passed), `pnpm test:integration` (32 passed including parent suites), `pnpm test:system` (real production HTTP lock/save race, reports and XLSX), `pnpm db:check-migrations`, `pnpm exec drizzle-kit check`, `pnpm db:generate --name verify_phase5` (no changes), lint, typecheck, formatting and production build all passed. No dependency was added.
